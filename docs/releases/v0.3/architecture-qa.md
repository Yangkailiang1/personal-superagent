# V0.3 架构问答

## 为什么需要多个 Agent？

用于划分上下文、职责和权限：主助手管目标和交付，writer 整理材料，reviewer 独立检查。任务本身简单时主助手不必强行委派。多角色只有在结果更清楚、权限更明确或上下文更可控时才有价值，不以角色数量证明先进。

## 子任务和业务任务为什么不放同一队列？

Task 是用户授权的目标，Attempt 是一次尝试；图内委派只服务这次尝试。SubTask 是可追溯展示，不允许用户把它单独重新启动，否则会和 LangGraph 的图状态竞争。需要独立交付和调度的工作将来才能升级为正式业务子任务。

## 用户审批时是不是一直占着服务器进程？

不是。原生 interrupt 先持久化状态，子进程退出，Worker 保存审批并释放模型额度。批准后重新启动进程，用同一个 thread_id 和 checkpoint 恢复。业务归属不释放，避免另一个 Attempt 同时修改同一任务。

## 为什么图状态用 SQLite，业务用 PostgreSQL？

当前单主机、每次执行独立文件，直接利用原生 saver，子进程不必持有业务数据库凭证。PostgreSQL 负责真正需要跨 Worker 并发事务的队列与业务状态。这不是适合所有规模的最终方案：多机恢复、集中备份与细粒度权限需求会推动后续存储调整。

## 两套存储会不会不一致？

会有崩溃窗口，不能说有跨存储原子提交。我们先提交 checkpoint，再把状态按稳定 ID 投影到业务表；确认旧进程停止后可重新读状态补齐。批准记录先持久化，产物必须与批准参数匹配，唯一约束防重复。测试故意删除业务投影，验证从 checkpoint 恢复。

## 模型能否绕过审批保存文件？

只靠提示词无法阻止。这里工具 schema 和实际执行都按角色过滤；原生文件/execute 被拒绝。保存工具必须经过 HITL，只更新图内文档状态，Worker 再检查批准记录才能发布。它不具备任意宿主文件写入能力，但整个 Python 进程不是 OS 沙箱。

## 恢复是否等于恰好执行一次？

不等于。LangGraph 可能重入一个未完成节点，外部副作用必须自行幂等。本版工具没有外部写入副作用，正式产物还有稳定 ID 去重。以后设备协议要使用操作 ID、执行确认和不确定结果处理，不能直接复用“收到请求就重跑”。

## 怎样控制费用与并发？

继承全局两个活动执行，每个 Attempt 的模型调用再限为一个；服务器一并发。图步数和活跃段超时是护栏，不是精确费用上限。当前未做 token 成本统计和真实供应商评测，不能声称已经解决所有成本治理。

## 服务器上跑起来是否算正式上线？

这里只是本人 SSH 隧道验证部署：没有公网入口、公开注册或默认密码。验证真实进程、数据库、审批和恢复有意义，但生产还缺完整配额、限速、监控、备份恢复演练与真实用户测试。报告会区分本地自动测试、服务器浏览器验收和未进行的付费模型验证。
