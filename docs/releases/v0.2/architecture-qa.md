# V0.2 架构问答：用实现解释设计

## 为什么不直接在 Django 请求中调用 Agent？

模型和工具是长任务，请求超时与业务取消不应该绑定。接口只做短事务入队，独立 Worker 执行。刷新或关闭网页只影响查询，任务状态仍由数据库和进程事实决定。代价是要实现领取、状态和恢复，而不是多开一个线程就结束。

## 业务状态与 LangGraph checkpoint 有什么区别？

Task/Attempt 回答“谁提交、执行到哪、结果是什么”；checkpoint 回答“图的状态和恢复节点是什么”。本版只有前者，所以重试重新运行，不声称可从中途恢复。下一版接 checkpoint 时，两者通过 Attempt 关联，但不能互相替代。

## 两个 Worker 怎么避免同一任务重复执行？

Task 行锁、skip_locked、Attempt 活动唯一约束三层配合。领取更新与事件在事务内完成；启动请求还有 request_key 幂等。全局额度使用事务级 advisory lock，避免两个 Worker 都判断还有空位。

## 为什么全局锁不会让两个任务变串行？

锁只覆盖毫秒级数据库领取事务，不覆盖模型执行。领取完成即释放，两个任务的独立子进程可以同时运行。自动测试实际启动了两个子进程，并验证它们执行时间区间重叠；这不是吞吐压测，不能据此宣称高并发能力。

## Worker 失联为什么不直接换一个 Worker 重跑？

心跳超时不等于进程停止，旧执行可能仍然调用模型或工具。先隔离旧结果，再确认进程退出，最后由用户显式重试。本版用领取 token 拒绝迟到结果，核对 PID 创建时间防 PID 重用。以后工具有写入副作用，还必须让工具本身支持操作 ID 幂等。

## 取消怎么保证与最后一条结果不冲突？

取消先落库。完成事务持有同一任务/执行锁，若取消已经提交，即使拿到结果也写取消而不是成功；若成功已提交，后来的取消不覆盖终态。只有确认子进程 wait 完成才释放归属。

## 多 Agent 应该怎样接在这里？

Task 仍是用户目标，Attempt 仍是本次尝试。V0.3 在执行图内增加主 Agent、受限子 Agent、计划及子任务关联，不另造第二套与业务任务竞争的状态源。先明确角色工具权限、结果契约、失败传播与审批，再考虑并行；Agent 数量不是项目复杂度指标。

## 你怎么排查“跑了很多步还没有完成”？

本版能检查 Attempt 的输入快照、运行模式、事件序列、工具重复次数、领取/心跳/终态和失败类型；设置图步数上限、请求超时及任务总时限。尚未实现 token 成本统计和调用级 tracing，所以不会声称已经能准确归因到成本或模型内部思考。后续增加观测必须控制日志敏感信息和用户访问权限。

## 本版能称为生产系统吗？

不能。它是有真实 PostgreSQL、子进程和故障验证的执行底座，尚缺完整多用户服务配额、登录限速、HTTPS 部署、备份恢复演练和本地工具授权。真实供应商任务成功率、成本与服务器容量也未实测。
