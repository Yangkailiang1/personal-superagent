# V0.5 架构问答

**为什么不是一个模型完成对话和执行？**

接待阶段需要讨论和修改，执行阶段需要冻结输入与权限。分工允许用户批准明确需求，并追溯某次执行基于哪版草稿；不是为了增加 Agent 数量。

**为什么接待也要 Worker？**

工具调用可能持续多轮。HTTP 只保存输入，Worker 子进程执行，网页关闭不终止模型。共用 Attempt 底座使两层遵守同一并发和恢复规则。

**如何防止模型自己入队？**

接待图只暴露 update_draft，执行入口也白名单检查。正式确认是带 Session/CSRF 的用户 API，事务检查版本、问题与假设，模型没有对应工具。

**看板是不是进度状态的事实来源？**

不是。Task、Attempt、审批和本地操作是事实，看板只是后端投影。没有进度百分比，没有拖动绕过审批。运行中活动来自已记录的角色与工具事件。

**为什么 Key 配置好了还需要验证？**

Key 非空不能证明服务支持工具调用。显式验证检查模型实际提出工具调用并正确读取结果；即使通过，也不等于真实多 Agent 任务成功率已经达标。完整真实任务验收仍需单独记录。

**如何避免并发修改草稿丢失？**

每次编辑/确认检查版本。前端冻结编辑起点版本，不拿轮询的新版本号覆盖旧内容。执行期间禁止编辑，结果投影也检查调用时版本。

**Exactly-once 是如何做到的？**

不声称通用副作用 exactly-once。确认通过事务和唯一约束幂等建任务；本地工具仍沿用 V0.4 的账本、租约与未知结果处理，不自动重放。
