# V0.4 架构问答

## 对话 Agent 和工作 Agent 是两层吗？

可以这样理解职责，但系统不止两个模型。接待层负责澄清和形成任务；持久化队列与 Worker 确保后台执行；执行图内又可以有多个专业角色。我们的 Task/Attempt/Worker 已实现，V0.4 加本地工具端；长期接待会话还未实现，不能把输入框换成聊天样式就声称拥有接待 Agent。

## 为什么任务不是由模型直接抢？

重复启动、并发额度和归属属于确定性事务规则，应由数据库和 Worker 控制。模型可以建议拆分与角色，但不能绕过用户确认、授权和领取凭证。把“需要判断什么”与“必须保证什么”分开，才容易恢复和审计。

## 为什么不用 MCP 就自动连接用户电脑？

MCP 能规范工具调用，但不替我们完成账号绑定、设备凭证、目录授权、离线队列、未知结果和防重复副作用。本版先实现这一最小业务协议，后续可以把工具适配为 MCP，而不是用 MCP 掩盖缺失的安全与生命周期。

## 为什么用轮询而非 WebSocket？

当前本人/少量用户和低频轻量工具，短请求容易复用 Django/Gunicorn、鉴权与重连，不维持入站连接或长占 Web worker。代价是约 2 秒延迟和更多空请求。规模增加或需要实时流时再引入推送，操作 ID、租约、账本仍然必须保留。

## 客户端掉线后为什么不能直接重试写入？

网络没有返回不代表文件没写。先落 started 账本，写完落结果，再报告；重启只重发回执。若恰好在文件发布后、账本完成前崩溃，只能认定未知，不能证明没执行。本版还用新建不覆盖减轻重复影响，但不声称实现了所有外部副作用的恰好一次。

## 目录检查用 resolve 是否足够？

不够，检查后路径可能被换成符号链接。这里使用每层 O_NOFOLLOW 和持有的 dir_fd，根还核对设备号/inode。读取先确认普通文件，新建用不覆盖原子发布。这约束固定工具，不等于容器或 OS 沙箱。

## 用户解绑能立即停止正在发生的写入吗？

不能绝对保证。我们阻止后续领取、在开始前再次检查、拒绝迟到结果恢复任务；已经通过检查并正在本机执行的原子写入仍可能完成。因此 UI 报未知并要求核实，而不是谎称没有任何改动。

## 怎么保证升级不让旧审批丢失？

业务表按编号迁移，保留旧记录；原 V0.3 图定义按字节冻结，按 workflow_version 选择执行/恢复模块。新图改动不能覆盖旧 checkpoint。兼容有维护成本，未来应定义版本保留和迁移策略，而不是删除旧实现让用户重做任务。

## 为什么不同时把全套前台访谈 Agent 做完？

本版交付的是执行边界和可用工作台：设备、权限、工具结果和恢复先真实可靠。后续接待 Agent 才能在明确能力范围内承诺任务，形成草稿并经确认入队。它不能在设备未授权、任务未启动时就宣称已经替用户执行。
